Felan · Codebase Memory extension · A/B

Does Codebase Memory pay off?

Two coding tasks, run with the Codebase Memory extension off and on, everything else held identical. Each task's headline cost signal turned out to be an incidental agent behaviour — an unfiltered grep in Phase 1, build polling in Phase 2 — each worth more per run than CBM's own effect. CBM's real intrinsic cost is about +11–20%, correctness is a wash, and it earned no win even on the wide-traversal task.

01

What was measured

Codebase Memory (@felan-ai/ext-codebase-memory) is a proxy over the native codebase-memory-mcp binary. It builds a structural graph of the repository at session start and exposes symbol lookup, caller/impact queries, and indexed text search, on the premise that this beats file-by-file grep and read on tasks that traverse many files.

The benchmark runs one task at a time against two Felan profiles that differ by a single flag. Prompt, starting workspace, model, thinking level, verifier, timeout and credentials are all held constant.

Phase 1 — a localized task

Objective: minimize cost at equal correctness. Hypothesis: on a single-package task CBM should be neutral-to-negative — its tool schemas cost tokens every turn and it indexes at session start.

The task is a real historical Felan regression: session creation must load the project's root AGENTS.md / CLAUDE.md through AgentRuntime with exact precedence and non-fatal rules. All edits land inside packages/agent-core/src. It was chosen to prove the pipeline, not to showcase CBM.

03

Root cause — the gap is a grep accident

Beyond the standard benchmark report. Offline analysis of the seven saved steps/run/stdout.log streams: per-request message.usage for billing, tool_execution args joined to results for payloads. Each tool result weighted by how many later requests re-send it — what actually gets billed.

Cost on this task is 68–89% prompt-side. Output tokens and request counts are near-identical across arms. The entire gap is context carried per request — so the question is only: what enters the transcript and stays there?

The blob: grep -R over dist/ matching source maps

Every run — all three CBM-off included — reads Pi's bundled node_modules/@earendil-works/pi-coding-agent/dist, first touch at request 3–5 in both arms. The task requires it: the regression is about Pi's ResourceLoader, which ships as bundled JS. What differs is only how the grep was phrased.

dist/ contains .js.map files. A source map is one line holding the whole original source. grep -R prints whole matching lines; head -N bounds lines, not bytes. Decomposing one CBM-on result:

Who restricted file types on the first attempt: off·1, off·2, on·1. Who did not: off·3, the smoke run, on·2, on·3. 1-in-3 CBM-off versus 3-in-4 CBM-on is a coin flip at this n. No CBM mechanism was found behind it — failed CBM lookups send the agent to sed on Felan source, which is cheap.

Not a truncation bug: ext-codex's truncateOutput fired correctly (301,314 → ~30,000 tokens). The lever is that the model may request max_output_tokens up to a 4 MiB ceiling, and these runs asked 20k–60k on exactly the dist greps.

CBM's actual intrinsic overhead

  • Fixed preamble: +509 tokens/request. The first-request prompt is exactly 1,761 for every Phase-1 CBM-off run and 2,270 for every CBM-on run — 4 tool schemas plus the capability paragraph. The same +509 delta holds in Phase 2 at a higher baseline (2,331 / 2,840), a clean cross-check on the method. Over 14–19 requests: <1% of the bill.
  • Grep augmentation: negligible in Phase 1 (4–10 results per on-run, nearly all results: 0) — but material in Phase 2, where the graph matches. See section 05.
  • CBM payloads: 7–20% of prompt tokens. 6–10 calls per run, 7–10k raw tokens, but they land early and ride everything after → 84k–147k carried. Almost all of it is search_and_read_symbols at 5–19 KB per call.

Cleanest controlled pair, both blob-free: on·1 $0.847 versus off·2 $0.762 — +11%.

04

Extension defects found along the way

All in Felan's ext-codebase-memory, none in codebase-memory-mcp 0.10.8 (verified against the real binary on a throwaway 2-file repo).

Defect · blocking

read_symbol returned source 0 times in 29 calls

Across every CBM-on run in both phases (0 / 14 Phase 1, 0 / 15 Phase 2). Two independent bugs in services.ts:

  • qualified_name path (8 calls, candidates: []): the extension sends qn_pattern; the binary answers pattern queries with a grouped envelope, not the flat one it returns for query. searchCandidates() handles only the flat shape, so a real match (total: 1) parses as zero.
  • name + file_path path (6 calls, error despite candidates: 1): the filter reads candidate.file_path, but the column is file — the comparison is always false.
  • Masked by unit tests that stub search_graph in a shape the binary never emits; the e2e test only asserts the tools are registered.

Consequence: with read_symbol dead, search_and_read_symbols (~15 KB) is the only working read path where a targeted read would be ~1.4 KB. Fixing it should make CBM both useful and cheaper.

Defect · minor

search_and_read_symbols returns a redundant candidate list

The full search_graph result (limit 20) is returned next to snippets for only read_limit (default 6). Across 9 calls the candidate blocks total 26,260 B, of which 51% duplicates symbols[].symbol verbatim. Small in absolute terms.

The confound: build polling

exec_command takes a yield_time_ms. When a monorepo build outlives it, the agent polls with write_stdin — and every poll is a full request that re-sends the whole conversation. Every poll in these runs waited on the same commands (pnpm --filter './packages/ext-*' build, agent-core build && ext-* build, felan build && test) in both arms. What differed was the slicing: all four CBM-off runs polled at yield_time_ms: 1000; two of five CBM-on runs used 30000 and barely polled.

No exploration saving either. Raw bytes read are comparable (tightened prompt: off 39.6 k tokens vs on 45.4 k, +15%). CBM shifts ~20% of the reading into structural queries and pays it back in payloads — and here grep augmentation is material: the graph matches, so every augmented grep returns 20 results at ~3 KB, the same ~2,947-byte block repeating across 3–4 greps — 23 k–225 k carried tokens, up to a third of CBM's footprint. Both arms still cat every ext-*/src/config.ts in a shell loop (37–88 KB).

06

What to conclude

Direction-aware gain on the declared objective (minimize cost). Positive = Codebase Memory is cheaper. Faint = raw headline; hatched = after removing that phase's confound.

Phase 1 · localizedraw −92% → real −11 to −20%

Faint bar = raw −92% median. Hatched = CBM's intrinsic overhead once the grep/source-map blob is removed: −11% to −20%.

Phase 2 · wide fan-outraw +9% → work −27 to +5%

Faint bar = raw +9% median — an artifact of CBM-off runs spending 12–27 requests each on build polling (3–14 for the passing CBM-on runs). Hatched = work-cost with poll-turns removed: straddles zero, leans against CBM-on, n small.

−100% −50% 0 +25%

The read

  • Correctness is a wash. Every clean run in both phases produced a correct solution. CBM neither helped nor hurt accuracy.
  • Twice, the headline cost signal was an incidental agent behaviour, not CBM. Phase 1: an unfiltered grep matching .js.map files (~$0.5–1.5/run). Phase 2: 1-second build polling, each poll a full request (~$0.3–1.5/run). Both larger than CBM's real effect in either direction.
  • CBM's real intrinsic cost is small — about +11–20%. Fixed preamble, plus search_and_read_symbols payloads that land early and ride the whole transcript, plus — in Phase 2 — grep augmentation.
  • No win on wide traversal. On work-cost (polling removed) the arms are within noise on the original prompt and CBM-on is worse on the tightened one — largely because read_symbol is broken, forcing the ~10× heavier search_and_read_symbols as the only read path.
  • At n = 3, this benchmark cannot resolve a 10–20% effect. The incidental confounds are bigger than the thing being measured.

Recommendations

  • Fix read_symbol first, then re-benchmark. The current numbers measure a degraded extension.
  • Neutralise both confounds: cap exec_command output per line (a source-map line is 119 k chars) and enforce the token ceiling; fix yield_time_ms for build commands, or exclude poll-turns from the cost metric.
  • Raise n or declare a formal benchmarks: entry before quoting a headline effect size.
  • On today's evidence: CBM is cost-neutral-to-slightly-negative and correctness-neutral — keep it off by default, and revisit only after the read path is fixed.

Method & caveats

This is not the framework's formal benchmark report. Runs were ad-hoc run --case … --agents … invocations, not stamped to a declared benchmarks: id, so they carry no definition digest and mix a thinking: max smoke run, two Phase-2 prompt versions, and replaced failures. Figures are one model (gpt-5.6-sol), thinking: medium, single-repo, n = 3 per arm.

Root-cause analysis is offline transcript decomposition from saved steps/run/stdout.log streams: per-request message.usage for billing, tool args joined to results for payloads, each result weighted by tokens × requests-remaining. A request is a poll-turn when every tool call in it was write_stdin. Category sums land within ~3–25% of measured prompt totals, so treat shares as approximate and ordering as solid. The Phase-2 poll-split analysis was cross-checked by a second independent pass.
